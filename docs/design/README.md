# ORB DUEL 表现设计入口

这是一套工作方法，不是新的战斗规则。先问“观众应该感受到什么、看懂什么”，再决定动画、声音、粒子、镜头和提示。夸张可以服务角色与关键时刻，不能靠无差别放大、延长停顿或堆粒子代替设计。

搜索外部视觉参考前，必须遵守[视觉参考素材规范](VISUAL_REFERENCES.md)：优先适配2D平面实战的动态素材，按视角、动作、视觉语言、规模、可迁移性筛选。不要把元素相似当作适合，更不能用局部刀光参考代替整套人刃协同的动作参考。

## 按任务读取

需要理解设计原理、心理依据、案例和误用时，进入 [游戏表现知识库](knowledge/README.md)。它按八个专题保存研究，并区分已读来源、设计推导与待验证问题；不必每次通读，也不替代以下项目规范。

制作新特效前按需查看[已确认的视觉风格与反例](STYLE_ANCHORS.md)，实际打开相关锚点图；用户已选择简洁的代码绘制 2D 血刃方向。

## 当前结构审计（2026-10-15）

- 正式代码在 `outputs/orb-duel/`，独立静态脚本，无构建依赖。`work/` 不是运行入口。
- `engine.js` / `team-engine.js`：固定时间步长、模拟时钟、暂停与全局顿帧。`physics.js`、`skills.js`及角色模块拥有真实运动、命中与结算。
- `renderer.js`、各 `*-render.js`、`spectacle.js`：Canvas 表现。`audio.js`：本地合成、并发限制、混音。正式目录没有使用下载的 Kenney 音频；已有 PNG 多为历史预览，并非运行素材。
- `effects`、`soundEvents`、`signal/notice`分开调用，已有局部角色阶段，但缺少跨通道的共同事件标识。已有独立 `fxRng`；新表现工具进一步使用自己的事件哈希，不消耗这两个随机流。
- 历史专项页面和 `work/check-*.cjs` 能生成机制帧，路径、选种、采集与评审格式较分散。本轮增加共同实验室，不删除这些有用的专项验证。
- 当前奥义实现包含上一轮中断前的改动；不能把现有长停顿当成规范认可的最终节奏。本轮保留角色源码，不顺便完成或回滚那次角色迭代。

## 每项改动先写一张小卡

通常在任务说明或评审 JSON 中完成即可，无需每次新建文档：

> **感受与信息**：想让观众感到什么？必须看清谁、朝哪里、是否命中？  
> **不变的规则**：命中、伤害、范围、预瞄、无敌、冷却、反弹等边界。  
> **节奏**：阶段 / 触发事实 / 视觉 / 声音 / 停顿目的 / 退出或打断。  
> **强度与身份**：相对普攻、强化、觉醒、奥义的层级；角色的独特形状、运动和音色。  
> **证据**：种子、模式、场景、关键帧、连续播放、声音和要验证的边界。

普通球的最新演出意图是一个具体例子：**快速闪到背后（残影，无拳影、无停顿）→到位后蓄势停顿建立预期→猛然出拳→命中短顿帧→击飞与收尾**。这是后续角色改动的目标示例，不代表本轮已经改成这样，也不要求其他技能照抄。

## 职责与完成标准

同一次开发要兼顾手感设计、技术美术、动画、音效和体验评审。可以一人完成；职责不等于必须建立多个代理或文档。程序检查解决正确性与可重复性，观察和试听解决观感。最终报告分别列出“工具通过”“已观察”“已试听”“仍待判断”，不能用波形有效、截图存在或代码通过代替品质结论。
