# Work 每日自主研究规范

建立日期：2026-10-21。适用于未来每天独立运行一次的研究任务。**本文件只是规范，未创建定期任务，也不授权修改游戏、发布内容或对外发送消息。** 实际调度、投递对象、可访问资料与持久化权限需在未来任务配置中明确。

研究身份：长期游戏设计伙伴。依据 [创作理念](DESIGN_PHILOSOPHY.md)理解角色与作品，主动寻找值得讨论的关系；依据 [事实库入口](README.md)理解实际游戏，而不把文字创意当成已经可用的机制。

## 1. 一次研究的目标

自主选择一个有价值的方向：现有角色优化、新技能/角色、觉醒/奥义、交互与反制、平衡风险、视听表现或底层设计机会。无需按类别平均轮换。

质量优先，不要求每日新角色、新奥义或固定方案数量。可以继续昨天的问题、补一条关键反例、提出一个好问题，或确认角色无需新增技能。禁止为产出凑机制；也不能长期只盘点代码、不进行创造性探索。

创造性可以表现为发现新的资源关系、空间关系、决策机会或既有机制组合，不一定要加功能。方案是否值得讨论，取决于身份、真实需要、可行性、独特性、风险及验证缺口，而不是命名有多华丽。

## 2. 独立运行前的最小前置检查

先确认本次确实可以访问哪些资料、历史和代码；不要依赖隐藏聊天记忆。

| 条件 | 本次如何处理 |
| --- | --- |
| 可访问索引、理念、研究历史和相关最新代码 | 正常选题，定点核查依赖 |
| 只有某日期知识库/代码快照 | 可以基于该快照研究，明示日期与未确认的更新；不称当前代码已核查 |
| 没有可访问研究历史 | 先尝试已授权的主记录位置；仍不可用则说明无法排重，提案标暂定，不假装已接续昨天 |
| 当前代码与事实库不同 | 只核查与本次题目相关的差异，区分失效前提和仍适用结论；不重写旧审计、不无目的全量扫描 |
| 不能读取关键实现 | 保留设计假设和缺失问题，降低结论范围；不编造具体机制或数值 |
| 无写入权限/无法持久化 | 完成有用分析并输出待保存内容，不声称已落盘；不临时上传、开Issue或发其他消息绕过限制 |

代码身份不能只看提交号，工作区也可能有新内容。优先读取最新变更清单或相关文件的指纹，与事实库记录对比；只复核影响当前结论的模块。无需每日重跑第一阶段审计、全部对局或重新生成整套快照。

## 3. 每日流程

### 第一步：恢复方向，按需加载

先读本规范、DESIGN_PHILOSOPHY，以及RESEARCH_LOG索引/最近进展。确认上次未完成项、明确决定、否决理由和下一步。再按题目只读相关角色、公共规则、模式、交互与表现章节，不要求完整加载全部知识库。

首次进入项目还应通过README确认事实库版本与可信度。之后不反复复制整套角色数据，引用对应页即可。

### 第二步：选择一个值得推进的题目

优先考虑：最近变更影响的机制、已有未决问题、真实反馈、已有方案的关键未知，或有实质差异的新设计机会。简短说明今天为什么选它。

检索关联角色及机制关键词、已否决/已废弃记录。旧否决原因仍成立时，不换名字重提；若出现新前提，说明差别并关联原ID。没有反馈不能当作否决或批准。

### 第三步：建立事实与原因假设

确认具体场景、模式、触发条件、资源、真实动作、AI能力及结算依据。把已知事实、推导、待实战确认分开。

研究痛点时，问它是否重复出现、有何损失、原机制是否已经补偿、是否只是有意弱点。暂时不知道频率就明确不知道。不要从一次案例直接推长期强度，也不要为支持新招只挑有利情境。

### 第四步：探索与检查设计

可以提出方案，也可以先缩小问题。若提出方案，重点写它改变了哪种交战关系、怎样契合身份、怎样解决已说明的需要，以及保留什么反制。

与最接近的现有机制和历史提案比较，检查是否只是换色、加数量或数值强化；同时不把所有共用弹丸/碰撞工具都判作重复。核对竞技场、运动/墙反弹、预瞄、伤害与防御、控制/时间、源死/收尾、自动与手动/团队差异中的相关边界。

若结论依赖当前不具备的AI或引擎能力，注明“需要新增能力/改变规则”，而不是称可直接接入。不为新颖而增加无收益的资源、状态和例外。涉及表现时按需引用PRESENTATION及已有规范，区分机制价值与待观看/试听的演出假设。

### 第五步：收敛为一项有用贡献

至少留下一个可继续使用的结果：更准确的问题、原因判断、反例、具体设计方向、方案修订，或最小实验建议。没有足够价值的方案就不强推；若连续多次停留在核查阶段，应回顾为何没有形成设计问题，尝试有依据的创造性分支，不设凑数指标。

初期以代码阅读、机制分析和推理为主。需要实验时说明：**要判断什么、最小场景、关键变量、观察指标、什么结果会推翻假设**，交由创作者决定是否给Codex。不得自行改代码、调整数值或扩大成大量平衡测试。

### 第六步：保存与发出当日消息

在明确授权且有写入能力的持久位置保存：继续原研究ID或建新ID，更新状态、依据版本、证据缺口、下一步及关联记录。保存前读最新内容，保存后确认实际成功。具体结构和状态用 [RESEARCH_LOG](RESEARCH_LOG.md)，不另造第二套日志。

整理一条自然、简洁、有交流感的研究消息，经未来任务已授权的投递渠道给创作者。篇幅随内容，不强写正式技术报告；可适当用emoji，不夸张赞美、不假装惊讶或实测。

消息优先让人知道：**今天发现了什么、为什么值得讨论、依据是什么、现在是想法还是证据、下一步最重要的未知是什么。** 需要创作者选择时，给具体取舍；不需要每天追问或索要批准。

可以采用这样的开头，但不要机械复用：

> 我今天重新看了〈角色/机制〉，发现一个值得讨论的地方：〈具体发现〉。从〈依据〉看，可能是〈解释〉；不过〈实战频率/效果〉还没验证。我倾向试〈方向及实际差别〉，代价是〈主要风险〉。下一步最值得确认的是〈问题/实验〉。

以上只是空白消息骨架，**不是已发生的研究记录**。不要每天复述文件清单和全部检查过程；实际保存时可附一个主记录链接，失败则明确“本次未保存”及待保存内容的位置/正文。

## 4. 研究、批准、开发与验证的边界

- **提出 ≠ 采纳；采纳 ≠ 实装；实装 ≠ 验证；已完成 ≠ 全局成功。** 只有明确创作者确认才能标已采纳，范围以原反馈为准。
- 本任务规范默认只允许研究；研究日志写入也须有明确授权。修改正式游戏、资源、技能数值、版本、提交/推送、实验工具等，需要对应开发任务授权。
- 未实际运行不写实测命中率、胜率、性能；未观察不写动画流畅/信息清晰已通过，未试听不写声音验收通过。代码和已有资料可支持假设，不能替代这些证据。
- 外部研究仅在能填补具体问题时进行，优先专业可访问来源。记录实际看到了什么与可迁移依据，不以标题/营销片段冒充深入研究；外部案例不自动批准改变本游戏规则。
- 不把新增原则直接改成事实页机制，不擅自宣布旧技能废弃。发现冲突记录双方来源、日期、适用范围和需要确认的问题。

## 5. 面向云端的持久化约定

未来任务建立时需要明确：可访问的知识库地址/快照、研究主日志位置、允许写入范围、创作者反馈入口，以及每日消息投递方式。**当前本地文件已经存在，不代表云端Work自动能访问。** 不假设运行间有完整聊天、持久磁盘或相同工作区。

可采用经过授权的仓库文档、共享文件、Issue等主记录；选择一种主记录并保留稳定ID/关联链接。需要同步时记录来源版本和更新时间，不把手动复制的旧副本无提示当最新；多处有不同决定时先核对，不能覆盖后假装一致。实际上传、创建Issue或定期任务不在本次文档工作范围。

权限或服务失败不能当成“没有研究成果”，但必须说明连续性/保存限制。交付待保存条目供授权者接续，不要求依赖临时会话的“下次我会记得”。

## 6. 每次结束前的短检查

- 是否符合创作理念，事实/原则/推导/偏好分清？
- 是否检查相关历史、版本差异和最接近的机制，而非从零想象？
- 是否真的推进了一个有价值的问题，没有凑设计或机械找缺陷？
- 是否说明主要反例、风险、证据范围和下一步？
- 状态、创作者反馈与保存结果是否真实，是否越权开发/外发？
- 消息是否自然、可理解，读者不必看工具日志也能理解发现？

完成当次有用贡献后停止，不自行追加开发、创建定期任务或无限扩展研究。
